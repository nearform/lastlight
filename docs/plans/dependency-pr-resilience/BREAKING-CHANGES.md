# Breaking changes — dependency-PR resilience

A running record of every behaviour change in this work that an existing
deployment would notice on upgrade. Last Light has very few users, so the plan
deliberately prefers a clean break over a compatibility shim — but every break
is recorded here, with the migration, so the release notes can be assembled from
this file.

Entries are appended as each phase lands.

## Policy defaults chosen at execution time

Three of the README's open questions were settled by the operator before any code landed. Each overrides the phase doc's own recommendation in favour of delivering the issue's actual ask, on the basis that Last Light has very few deployments and a clean break is cheaper than a compatibility shim.

| Key | Plan recommended | **Shipped** | Effect on upgrade |
|---|---|---|---|
| `dependencies.autoMergeMaxImpact` | `low` | **`medium`** | Low- **and** medium-impact major version bumps auto-merge on every deployment, rather than requiring `medium` to be set in an overlay. This is issue #252's actual ask. High-impact majors still get `requires-human` — by the agent's own hand: the ceiling is prompt-level, see Phase 5 below. |
| `review.trigger` | `eager` (today's behaviour) | **`after-checks`** | `pr-review` no longer fires on `pr.opened` / `pr.synchronize` / `pr.reopened`. It runs once per settled head SHA, either colour, and can cite the CI result. Rapid pushes no longer produce a review per commit. |
| `review.skipDraft` | `true` | **`true`** | Draft PRs are no longer reviewed on the webhook path, matching what the cron has always done. `ready_for_review` becomes the event that triggers the review. |

## Deviations from the plan's locked decisions

- **README locked decision 8 — "No changes to `packages/workflow-engine/`" — is not held.** That decision rested on "every capability needed already exists". It does not, and it turned out to be wrong twice:
  - 09's locked decisions 7 and 9 require a diagnosis of `flaky` / `infra-dependent` / `upstream-broken` to skip the `fix` phase while the run still records `succeeded`, and the engine had no phase-level conditional skip. A minimal `skip_if:` was added, reusing the scheduler's existing non-failing-skip mechanism and `loop-eval.ts`'s existing safe expression evaluator.
  - **`generic_loop` silently ignored `on_output.requires_marker`.** Only `runStandard` enforced the postcondition, so giving the `fix` phase the §4.5 gate loop would have dropped its `CI_FIX_COMPLETE` requirement without a word — reintroducing, on exactly the phase Phase 2 added the marker to protect, the silent no-op the marker exists to catch. `runGenericLoop` now checks the marker against the **last** iteration's output. Reaching `max_iterations` without the loop condition is deliberately *not* a failure (a fix loop that runs out of iterations reports `outcome=gave-up`, which is a correct outcome); only the absent sign-off is.
- **A third engine deviation, smaller:** a `generic_loop` phase now emits its `messages.on_start` / `on_success` / `on_failure` the way a standard phase always has. Inert for the only pre-existing production consumer (`explore.yaml`'s `socratic` phase declares no `messages:` block); it is what makes the two fix phases keep their existing progress messages once they became loops.

## Pre-existing bugs found during execution (not introduced by this work)

- **The dispatcher's double-dispatch guard has never worked.** `dispatcher.ts:133` calls `db.executions.isRunning(handler, triggerId)` with a bare workflow name (`"pr-fix"`) and a bare issue number (`"42"`), but every phase row is written by `phase-executor.ts` with `skill = "<workflow>:<phase>"` and `trigger_id = "owner/repo#N"`. No row can ever match on both predicates, so the guard whose comment reads *"Guard against double-dispatching the same work"* has been a no-op for every workflow. Phase 3′'s PR-scoped lock replaces it, and this is why that lock matters more than the plan assumed.
- **`apps/www/src/pages/docs/configuration.astro` documents a `WORKFLOW_DIR` env var that does not exist.** `spec/02-configuration.md` states explicitly that there is no `WORKFLOW_DIR` and no `workflowDir` field — assets resolve layer-wise. Left as-is (out of scope), but it misleads anyone setting up an instance.
- **The site claimed the wrong phase counts for both fix workflows** — `pr-fix` was described as single-phase and the workflows overview card said "1 phase", while the `dependabot-ci-fix` card claimed "2 phases" when it had one. Corrected as part of Phase 2's docs.
- **The dashboard's mirrored `RepoMergedConfig` / `RepoConfigSources` types** (`apps/server/dashboard/src/api.ts`) do not carry the new policy blocks, so the per-repo Config tab will not render them. Display-only; recorded as a follow-up.

## Phase 6 — the `fix:` / `dependencies:` config blocks

- **`dependencies.autoMergeMaxImpact` ships `medium`**, so low- and medium-impact major bumps auto-merge on every deployment (see the table above). Set it to `none` in an overlay to keep today's escalate-every-major behaviour.
- **`review.trigger: after-checks` and `review.skipDraft: true` ship packaged** (see the table above). Inert until Phase 7 consumes them.
- **`dependencies.minSettledChecks: 1` is operator-only** and cannot be lowered by a repo. A genuinely CI-less repo therefore stops auto-merging dependency PRs on upgrade. This is deliberate: §6.2's `max(repo, operator)` clamp would have welded the escape hatch shut in the direction people need it, so the CI-less case is handled on the fact (`checksState === "none"` blocks *major* auto-merge only) rather than on the policy.
- **`fix.maxCostUsd` ships at `5.0`, on** — a cumulative per-PR ceiling across attempts. A brake that ships disconnected is not a brake.
- **`review.afterChecks` does not exist.** The `passing` variant was a footgun in combination with the fix loop: a PR we gave up on never goes green, so the escalated PRs — the ones most needing human eyes — would have been the only ones never reviewed.
- **New repo-settable keys**: `fix`, `dependencies` and `review` are appended to `DEFAULT_REPO_CONFIG_ALLOW_KEYS`. A repo may only ever be *more* conservative; a loosening leaf is dropped with a new `policy-downgrade` warning rather than failing the run.
- **`fix` and `dependencies` are seeded onto the template context; `review` deliberately is not.** `renderTemplate`'s `walkKey` resolves a dotted key against `ctx` before falling back to `ctx.phaseOutputs`, and `build.yaml`'s reviewer loop declares `output_var: review`, read by `prompts/pr.md` as `{{#if !review.approved}}` / `{{review.cycles}}`. A top-level `review` object would have shadowed it and made every build PR body claim unresolved reviewer issues. The same hazard applies to any future overlay workflow using `output_var: fix` or `output_var: dependencies`.

## Phase 1 — real CI evidence (`Actions: read`)

- **The GitHub App requests a new optional permission, `Actions: read`.** Every existing installation must re-consent to grant it. Nothing hard-fails without it — the CI failure report degrades to check-run annotations exactly as before — but the degradation is now *stated* in `{{ciSection}}` instead of being invisible, and diagnosis quality is capped at annotations until it is granted.
- **`agentic-pi`'s `read` profile grew from 18 tools to 21** (`github_list_workflow_runs`, `github_list_workflow_run_jobs`, `github_get_job_logs`), and every other profile by the same three. Any consumer pinning a profile's tool count sees the change.
- `packages/agentic-pi/test/fixtures/phase2-smoke-github-read-profile.jsonl` has been **re-captured** from a real run and records `toolCount: 21`. Captured evidence, never hand-edited: the smoke command in `packages/agentic-pi/CLAUDE.md` produces it, and now specifies a clean env + `--no-skills` so the capture carries no trace of whoever ran it. A `GITHUB_TOKEN` suffices for the `read` profile; the App PEM is not needed.

## Phase 2 — the `fixing` skill and the `diagnose` phase

- **`pr-fix` and `dependabot-ci-fix` gained a `diagnose` phase.** Both now run `diagnose` → `fix` instead of `fix` alone, so every fix run costs one extra (cheap) agent call. The phase resolves `{{models.diagnose}}`, which is unset in `config/default.yaml` and therefore falls through to `models.default`; an operator wanting the cost saving should pin a cheap model under `models.diagnose` in their overlay.
- **Both phases now require a completion marker.** `diagnose` fails without `DIAGNOSIS_COMPLETE`, `fix` without `CI_FIX_COMPLETE`. `dependabot-ci-fix` previously had no postcondition at all, so a run that inspected the PR and stopped without pushing or labelling reported green; it now reports red. An overlay that forks `prompts/pr-fix.md` or `prompts/dependabot-ci-fix.md` **must add the marker instruction** or every run of that workflow fails.
- **`skip_if` is a new phase-level field** (see the deviation above). It takes one expression or a list, OR-ed, in the `until:` grammar, and produces the same non-failing skip as `requires_sandbox` — the run still records `succeeded`. Purely additive: phases without it behave exactly as before.
- **A `flaky` / `infra-dependent` / `upstream-broken` diagnosis no longer reaches the `fix` phase**, so `messages.on_failure` ("leaving it for a human") no longer posts on those outcomes and no sandbox is provisioned for them.
- **`skills/fixing/` is new**, and both fix workflows moved from `skill: building` to `skills: [fixing, building]`. An overlay that overrides `skills/building/SKILL.md` is unaffected; one that pinned the phase's `skill:` field in a forked workflow YAML keeps its own value.

## Phase 3′ — the PR state machine

Added retrospectively: `0f1a872` landed without an entry here, and it shipped several changes an operator notices. Assembled from the commit, `spec/03-integrations.md`, `engine/router.ts` and `engine/dispatcher.ts`.

- **`pr.checks_failed` now fires on non-dependency PRs** whose head commit Last Light authored. This is the one change in the whole plan that can *raise* run volume on human PRs — it is what lets `pr-fix` learn whether its own push turned CI green, which it previously could never see. Bounded by the fix loop's own attempt cap and cost ceiling, and by the fact that only a head **we** authored qualifies.
- **`pr.checks_failed` routes deterministically, with no classifier call** — dependency PR → `dependabot-ci-fix`, anything else → `pr-fix`, off the discriminator the connector already computed. This is not an optimisation, it is a correctness fix: `fallbackWorkflowForIntent` resolves a workflow by its `classification.intent` and `pr-fix.yaml` has no `classification:` block, so `pr-fix` was **structurally unselectable** and a human's red PR would have run a dependency-bump prompt, the `dependency-*` label vocabulary, and a `requires-human` preflight it was never designed for. Harmless only while the emit gate was dependency-only — which the bullet above changes.
- **One run per PR, across `pr-fix` / `dependabot-ci-fix` / `dependabot-pr-merge` / `pr-review`.** The loser is **dropped with a reason, not queued** (an explicit `@bot` request additionally gets a reply). Sound only because every dropped case has a cron re-pickup within a day; a future Phase 8 must convert drop-on-lock into queue-on-lock before removing any cron. This replaces a guard that never worked — see "Pre-existing bugs" above.
- **The fix family shares one workspace per PR** (`${repo}-${prNumber}-fix`, not `…-${workflowName}`), so attempt 2 reuses attempt 1's warm `node_modules` even when routing differed between the two fix workflows.
- **Three silent-result bugs fixed in the cron path.** The cron fan-out called `dispatchWorkflow` directly, bypassing `handlePrFix` — so every nightly `fix-red-dependency-prs` run carried an **empty `{{ciSection}}`** and no fork guard, while the webhook route carried `ciSection` but no `{{reason}}`. `headSha` was dropped. And `baseBranch` was the repo default rather than the PR's real base, so a PR targeting a release branch had the fix prompt merge the wrong base. One projection at one choke point makes both routes identical by construction.
- **Fork PRs are refused with a comment** rather than failing partway through: the harness cannot push to a fork's branch, so attempting it wasted a full sandbox run to discover that.

## Phase 5 — major-bump impact classification

- **Major version bumps can now merge automatically.** Every major used to become `dependency-functional` + `requires-human`, whatever it was. A major is now judged by the `dependency-impact` rubric and auto-merges at or below `dependencies.autoMergeMaxImpact`, which ships **`medium`** — so low- and medium-impact majors land unreviewed on every deployment. Set `autoMergeMaxImpact: none` in an overlay to keep today's escalate-every-major behaviour.
- **The impact ceiling is prompt-level; the settled-checks gate is the code-enforced half.** `dependencies.autoMergeMaxImpact` reaches the run only as prompt text (`workflows/prompts/dependabot-pr-merge.md`), the tier itself is the model's self-report in the `ASSESSMENT_COMPLETE` marker, and **no code parses `impact=` or compares it to the ceiling**. Nothing withholds the merge capability from a phase whose tier came back above it: `resolveMergeDisposition` (`src/engine/pr-decisions.ts`) hard-blocks only `checks pending`, `human-hold`, `escalated` and `already-assessed`, so a failing PR still reaches the phase that holds `github_merge_pull_request`. What is enforced in code is `mayMerge` — `requireSettledChecks` + `minSettledChecks` over the resolved check state — computed before the run and projected as `{{mayMerge}}` / `{{mayMergeReason}}` for the prompt to read rather than re-derive. This is not a regression (merging has always been agent-driven, and the phase must still run when it may not merge, because it also labels and comments), but it bounds what `autoMergeMaxImpact: medium` buys you and the docs must not oversell it as a safety property.
- **"TRIVIAL" changed meaning.** It now means *safe to land without a human*, not *small*, so a major bump can carry the `dependency-trivial` label. Anything downstream that read `dependency-trivial` as "not a major" is wrong now; the impact labels are how you tell.
- **Three new labels are created on managed repos**: `dependency-major-low` (`0e8a16`), `dependency-major-medium` (`fbca04`), `dependency-major-high` (`b60205`). The first major assessed in a repo creates them via `github_ensure_labels`, exactly like the existing three. Constants live beside `DEP_TRIVIAL_LABEL` in `src/cron/dependabot-discovery.ts`; `tests/cron/label-vocab.test.ts` pins both names and colours against the prompt. `dependency-functional` + `requires-human` keep their meaning, so cron discovery for the escalated case is unchanged.
- **The merge gate moved from `mergeable_state` to the code-computed check state, and now covers auto-merge too** (09 → D10). Four consequences an existing deployment sees:
  - A PR whose checks are still running or failing **no longer gets auto-merge enabled optimistically**. The old `unstable` / `blocked` / `unknown` branch enabled auto-merge and stopped; now it stops. The settled-checks webhook and the daily sweep bring the PR back once CI has spoken, so nothing is lost — but the "enabled auto-merge, waiting for CI" state disappears from Last Light's behaviour.
  - A repository with **no checks at all** (`checksState: none`) stops having its dependency PRs merged automatically — for *every* bump, not only majors, because `minSettledChecks: 1` is the gate. This is the behaviour reduction 09's `minSettledChecks` section flags; it is operator-only and cannot be lowered by a repo.
  - A `blocked` PR whose checks are green (a required *review* outstanding) still gets auto-merge, which is the case auto-merge genuinely exists for.
  - `mergeable_state` survives in the prompt only for branch hygiene (`behind` / `dirty`) and for choosing between the two merge mechanisms. The "confirm `mergeable_state` is exactly `clean` before direct-merging" instruction is gone — the gate already is that proof.
- **The `ASSESSMENT_COMPLETE` marker gained an `impact=` field**, between `verdict=` and `action=`. `requires_marker` matches the literal prefix so the postcondition is unaffected, but anything parsing the line by field position rather than by name sees a new field.
- **One extra comment per auto-merged major**, when `dependencies.auditComment` is on (the packaged default) — it records the impact tier and the evidence, and is the only durable answer to "why did this land unreviewed". It counts toward the prompt's existing two-comment maximum and is skipped when the impact label was already on the PR before the run, or when an equivalent comment is already there.
- **The assess phase stages two skills**: `skills: [code-review, dependency-impact]`. An overlay that forked `workflows/dependabot-pr-merge.yaml` keeps its own `skill: code-review` and will run the new prompt without the rubric — the prompt still states the tiers and the unknown⇒high rule, so it degrades rather than breaks, but the fork should be updated. A repo can override `skills/dependency-impact/SKILL.md` in its own `.lastlight/` with no change to `repoConfig.allowKeys`.
- **`mayMerge` is now the gate the merge prompt reads, rather than a predicate the prompt restates.** Phase 5 initially expressed the gate as prose over the `checksState` / `checksSettledPassing` / `settledCheckCount` facts, leaving `mayMerge` (`src/engine/pr-decisions.ts`) with no production caller — one predicate, two readings, free to disagree, which is the exact failure mode 09 exists to remove. They *did* disagree, in both directions: the prompt's `{{#if !checksSettledPassing}}` banner missed `settledCheckCount < minSettledChecks`, so an operator raising `minSettledChecks` was told the gate was open while it was shut; and it ignored the `requireSettledChecks: false` exemption, so a deployment that had turned the gate off was still told not to merge. `renderContext` now projects `{{mayMerge}}` + `{{mayMergeReason}}` and the prompt reads them. Effect on upgrade: those two configurations behave as documented instead of as written.

## Phase 4a — the marker harvest

- **Both fix workflows' marker lines are now parsed and persisted.** `RunnerCallbacks.onPhaseEnd` reads `DIAGNOSIS_COMPLETE` / `CI_FIX_COMPLETE` out of each phase's output and merges the parsed fields into `workflow_runs.scratch.fixMarkers`, where the next dispatch reads them back. Nothing about the marker *grammar* changed, so an overlay that forked the prompts keeps working — but one that reworded the marker line now loses `attempt` / `priorAttempts` / `flakyDeferrals` derivation silently, where previously there was nothing to lose.
- **`attempt` is now charged on the marker, not on the ledger.** The Phase 3′ seam approximated "did this run spend an attempt?" by asking whether the `diagnose` phase wrote a succeeded ledger row; it now reads the harvested class. The practical difference is 09's class table: `flaky` and `upstream-broken` are correct stopping verdicts about something other than this PR's code and no longer consume budget, where the ledger probe charged for them. A PR that kept diagnosing `flaky` used to burn its three attempts and escalate; it now defers (bounded by `fix.maxFlakyDeferrals`, below). Rows written before the harvest existed fall back to the old ledger probe, so an upgrade with fix runs already in flight does not miscount.
- **`{{maxAttempts}}` exists.** All three fix prompts already rendered `{{#if maxAttempts}} of {{maxAttempts}}{{/if}}` and it was never provided, so every prompt said "this is attempt 2" and never "of 3" — the half that tells the agent whether to spend or stop. It now renders.

## Phase 4c — the flaky cap and model escalation

- **A `flaky` diagnosis no longer defers forever.** After `fix.maxFlakyDeferrals` (packaged `2`) consecutive `flaky` verdicts on the same problem, the third is promoted to `reproducible`: the harness drops the `class=flaky` row from the `fix` phase's `skip_if` for that run and a normal attempt is spent. A PR that has been quietly deferring on the daily sweep gets one real fix attempt on upgrade. Three flaky reports running is an intermittent real failure, and the alternative is an unbounded series of free full runs on one flaky test. `infra-dependent` and `upstream-broken` are unaffected — they skip unconditionally, whatever the deferral count.
- **The `skip_if` list a run evaluates is now composed by the harness, not read verbatim from the YAML.** `promoteFlakyDiagnosis` (`src/workflows/simple.ts`) matches the expression `scratch.fixMarkers.diagnosis.class == 'flaky'` **literally**. An overlay that forked either fix workflow and reworded that expression — different quoting, a different needle, an added prefix — keeps today's behaviour and will defer on `flaky` forever, with no error. The engine's expression grammar was deliberately not extended to express the conjunction: it has no negation, and adding one for this is a wider blast radius than the problem.
- **The three `skip_if` rows now read the PARSED class, and a fork carrying the old rows fails in a NEW direction.** They were `phaseOutputs.diagnosis.contains('class=<cls>')` — a substring match on the diagnose agent's entire free-form output, which matched the agent's own prose ("this is not `class=flaky`, it is reproducible"), matched a `{{priorAttempts}}` line replayed from an earlier attempt, prefix-matched (`class=flaky-timeout` yes, `class=probably-flaky` no), and was **empty across a resume boundary**, where it failed open. They are now `scratch.fixMarkers.diagnosis.class == '<cls>'`, off the value the marker harvest already parsed and persisted on the run row. An overlay that forked either fix workflow and kept the old rows now **never matches at all**: nothing writes `phaseOutputs.diagnosis` into the guard's world any more that the harness will act on, so every `flaky` / `infra-dependent` / `upstream-broken` verdict runs the full `fix` phase — a sandbox and a 900 s gate — against a diagnosis that said there is nothing to do. That is worse than the old "defers forever" failure, because it spends money on every dispatch. Update the fork's three rows.
- **The engine refreshes `runScope.scratch` from the run row each iteration** (`packages/workflow-engine/src/core/scheduler.ts`), inside the `getRun` the cancel check already made — no extra query. A `scratch`-reading guard was otherwise a silent no-op on the fresh path, since the scope's copy predated the phase that wrote it. Any overlay or fork relying on `scratch` being frozen for a run's lifetime should note the change; nothing packaged did.
- **Both fix workflows' `requires_marker` now names the tag WITH its colon** (`DIAGNOSIS_COMPLETE:` / `CI_FIX_COMPLETE:`). The engine enforces the postcondition as a bare substring of the phase output while the parser only recognises `<TAG>:`, so the bare tag let an output that merely *mentioned* the tag pass a gate that then parsed to nothing — a green phase, a null diagnosis, and an attempt counter that could never advance. A forked fix workflow YAML still declaring the bare tag keeps that hole; the two strings are pinned to `DIAGNOSIS_MARKER_POSTCONDITION` / `CI_FIX_MARKER_POSTCONDITION` in `src/engine/fix-markers.ts`.
- **`models["pr-fix-retry"]` is now live.** Previously documented but inert; every attempt above `fix.escalateModelAfterAttempt` (packaged `1`, i.e. attempt 2 onward) now runs the `fix` phase on it. A deployment that already set the key as a no-op starts paying for that model on retries. Operators who set no `pr-fix-retry` key see no change at any attempt number. The substitution is applied before `context.models` is persisted, so the admin panel and a resumed run both show the model the attempt actually used, and it composes with a per-repo `models` override for free.

## Phase 4d — the within-run gate loop and the push gate

- **The `fix` phase of both fix workflows is now a `generic_loop`** (`max_iterations: 2`, `until_bash`, `fresh_context: false`) with an explicit `timeout_seconds: 900`. The timeout is load-bearing, not cosmetic: `runUntilBash` defaults to `timeout_seconds ?? 30`, and thirty seconds kills any real test suite mid-run and reports a false red.
- **`fix.localIterations` and `fix.gateTimeoutSeconds` are still not wired.** The phase schema parses `max_iterations` and `timeout_seconds` as plain numbers, so they cannot be templated from config; the YAML hardcodes values matching the packaged defaults (`2` and `900`). Changing either config key has no effect — change the workflow YAML, or fork it in an overlay. This is a known gap, not a decision.
- **The push gate moved into the checkout's `.git/`.** The `fixing` skill originally told the agent to write it at the *workspace root* (`../`), which is unreachable on **gondolin — the packaged default backend**, since gondolin mounts only cwd; the gate would silently never have run on a default deployment. The final path is `<repo>/.git/lastlight-verify.sh` on every backend. `.git/` is the repository, not the work tree, so git never walks it and `git add -A` cannot commit the gate anywhere — replacing the earlier `.git/info/exclude` registration, which each backend had to remember to write and which the kubernetes backend never did (issue #256). It also keeps `until_bash` a literal string (the engine's `validateShellCommand` rejects any command containing `{{`). **An overlay that forked `skills/fixing/SKILL.md` or any of `prompts/{diagnose-ci,pr-fix,dependabot-ci-fix}.md` still names the old path and its gate will never run — update the fork.** The prompts now render the path from `{{verifyScript}}` rather than hardcoding it, so a re-fork stays correct.
- **The harness deletes the gate script at the start of every attempt** and re-registers the exclude entry. The fix family shares one workspace per PR, so a script written by a superseded diagnosis — possibly by the *other* fix workflow — otherwise outlives the run that wrote it, and a stale gate is worse than no gate: it passes green against the wrong commands and authorises a push.
- **No gate is now an explicit red.** Absent script ⇒ the `until_bash` command exits non-zero deliberately and `gate=skipped` never authorises a push. Previously "no script yet exits non-zero and simply loops" worked only by accident of exit codes.

## Phase 4b — escalation actions on the PR

- **A PR the bot gives up on now gets a label and a comment where it previously got silence.** Three dispatch-gate skips are terminal for the current problem — `fix.maxAttempts` exhausted, `fix.maxCostUsd` exhausted, and a last diagnosis outside `fix.retryableClasses` — and each now applies `requires-human` and posts **one** comment naming the case, the attempts spent and each attempt's `class=` / `cause=`. Before this they were skipped with a reason in the server log and *nothing at all* on the PR. **On upgrade the existing `requires-human` backlog gets neither a label nor a comment**: a label on a PR one of our runs has touched resolves as OUR escalation (pinned to the head SHA that run saw) and is skipped silently as already-escalated, while a label on a PR no run of ours has ever touched is the maintainer's hand-applied hold and stays permanent. Neither latches the PR dead: anyone else's push re-arms the first case with no label to remove. The label + comment therefore appear on the PRs the *new* loop exhausts, not on the backlog.
- **The other skips are still silent, and deliberately so**: `upstream-broken` (not this PR's fault, self-heals), `fork-pr` (already has its own comment), `human-hold` / `escalated` (already escalated), `already-assessed` (a duplicate delivery). Anything scripting off `requires-human` should not expect it on those.
- **An escalating skip writes a `workflow_runs` row** — status `succeeded`, no phases, `current_phase: "escalated"`, `context.escalation = { case, reason, at }` beside the snapshot. It is not cosmetic: `escalatedAtSha` is read back off the prior run's `context.prState`, and a dispatch-time skip writes no row, so a row-less escalation would leave `requires-human` with no escalation SHA behind it — which the next dispatch reads as a *human's* permanent hold and latches the PR dead (09 → D1's general rule: no prior-run verdict may gate dispatch unless the skipping path writes a row). Consequences an operator sees: the dashboard's run list gains rows for PRs that never ran a phase, and `latestSucceededForTriggers` now sees them, so the per-SHA dedup also fires for the escalated head.
- **A prior diagnosis outside `fix.retryableClasses` now stops dispatch on the next event.** With the packaged `["reproducible", "env-mismatch"]` that means `infra-dependent` escalates immediately instead of spending the remaining attempts. `flaky` and `upstream-broken` are excluded by construction (they are the classes that also cost no attempt): one is a deferral bounded by `fix.maxFlakyDeferrals`, the other is about someone else's branch. Narrowing `retryableClasses` in an overlay therefore now has teeth at *dispatch*, not only inside a run.
- **`PrState` gained `priorDiagnosisClass`.** Unlike the other derived fields it is **not** carried across a run that diagnosed nothing (including our own escalation row), which is what keeps removing the label by hand a genuine retry rather than an instant re-escalation. Anything reading a persisted `context.prState` from an older row simply sees the field absent, which reads as `null`.
- **`GitHubClient.addLabels` is new** — the only harness-side label write, needed because the escalation fires before any sandbox exists so there is no agent to drive `github_*` tools. No new App permission: label writes are part of the `Issues: write` / `Pull requests: write` grants the App already holds.
- **The escalation writes the row before the label, and comments only behind a label that landed.** Every ordering has a crash window; this one chooses the harmless side. A failed label write leaves an escalation record with no label, so the guard does not bind and the next event escalates again — visible as a duplicate `workflow_runs` row rather than as a permanently-stuck PR.

## Phase 4e — the PR journal (`PrState.notes`)

- **`PrState` gained a required `notes: PrNote[]` field.** Anything constructing a `PrState` literal (tests, an eval fixture, a future overlay-side tool) must supply it. Reading a *persisted* snapshot is unaffected — an older `context.prState` simply has no `notes` key, which `coerceNotes` reads as an empty journal.
- **Agents can now write to durable per-PR memory, and the harness renders it back.** The `fixing` skill tells the agent to append `<kind>: <one line>` to `.git/lastlight-notes` in the checkout; `onPhaseEnd` drains that file into `scratch.fixMarkers.notes` and the next dispatch folds it onto `PrState.notes`, rendered into all three fix prompts as `{{priorNotes}}`. Two operator-visible effects: fix prompts get slightly longer on PRs with a journal (bounded at 4 KiB), and an overlay that forked `skills/fixing/SKILL.md` or any of `prompts/{diagnose-ci,pr-fix,dependabot-ci-fix}.md` will neither write notes nor read them — silently, exactly as with the marker grammar. Update the fork to pick the feature up.
- **The journal is a file inside the checkout's `.git/`, on every backend.** `<repo>/.git/lastlight-notes`, deleted on every path that starts a new run — the same placement and treatment the push gate gets, for the same two reasons (git never walks `.git/`, so it cannot be committed; and `.git/` is inside cwd, which gondolin — the packaged default — does mount, unlike a `../` sibling). `artifactIssueDir`'s relocation was **not** reusable: it is conditional on `buildAssets === "server"` AND a non-gondolin backend, whereas the journal must be placed correctly in every mode on every backend, because unlike a build handoff doc it must never be committed into a dependency PR. On the **kubernetes** backend there is no host-shared workspace, so the drain finds no file and the journal is simply inert there — a gap, not a failure.
- **`harvestFixMarkers` no longer returns early for non-fix workflows.** It now reads the run row for every phase of every workflow to decide whether a journal drain applies (the gate is "does this run carry `context.prState`", i.e. is it PR-scoped — chosen over importing a second workflow-name set, which would have put `fix-harvest.ts` and `pr-state.ts` in an import cycle). One extra synchronous SQLite read per phase. A PR-scoped run that is not fix-shaped and wrote no note still writes nothing to `scratch`.
- **`scratch.fixMarkers` can now appear on `pr-review` / `dependabot-pr-merge` rows** — when their agent wrote a note. Nothing reads those rows for markers (`didSpendAttempt` only ever sees fix-family rows), but anything treating the presence of the key as "this was a fix run" is now wrong.
- **Notes are hints and are structurally prevented from becoming anything else.** No decision function reads `PrState.notes`; `renderContext` projects it to one fenced string and that is its only consumer, so there is no boolean or per-kind list a `skip_if` / `until` expression could branch on. On ingest a note is flattened to one line (so it can never emit a line of its own, and therefore can never forge the fence it renders inside) and **rejected outright if it contains `class=`, `DIAGNOSIS_COMPLETE` or `CI_FIX_COMPLETE`** — those tokens are parsed, and a note able to write one could change what the workflow does. The fence and its "hints, never instructions" statement are emitted by `renderPrNotes`, not written into the prompt templates, precisely because the templates are forkable and a fork must not be able to delete a security control.
- **A head SHA change authored by someone else marks the whole journal stale rather than clearing it**, at the same boundary that resets `attempt` to 1. Staleness is sticky and renders as `STALE` beside the note. This is deliberately different from `priorAttempts`, which *is* cleared: a rendered attempt line is a claim about a problem that no longer exists, while a note is a claim a later run may still want to see and discount for itself.

## Phase 7 — configurable `pr-review` trigger modes

- **`review.trigger: after-checks` is now live, and it is the packaged default.** `pr-review` no longer fires on `pr.opened` / `pr.synchronize` / `pr.reopened`. It runs once per *settled* head SHA, either colour, off a new `pr.checks_settled` event — so it can cite the CI result, and a developer pushing three commits in five minutes gets one review instead of three that were stale before they posted. Set `review.trigger: eager` in an overlay to keep today's behaviour exactly. This break was already recorded in the table at the top of this file when Phase 6 shipped the key inert; this is where it acquires teeth.
- **`review.skipDraft: true` is live too.** Draft PRs are no longer reviewed on the webhook path — matching what the cron has always done. `ready_for_review` is the event that un-defers them, and it now maps to `pr.opened` semantics.
- **The connector emits three new event types.** `pr.checks_settled` (a settled suite on a PR neither check-outcome route claimed — emitted **only** under the operator's `after-checks`, since emitting is what costs event volume), `pr.labeled` (carrying `addedLabel`) and `pr.review_requested` (carrying `requestedReviewer`). Each has a `routes.github` entry — `pr_checks_settled` / `pr_labeled` / `pr_review_requested`, all defaulting to `pr-review` — so an overlay can redirect them; each also falls back to `routes.github.pr_review`, so an overlay that already pinned that one keeps working with no edit.
- **`labeled` left `IGNORED_ACTIONS`.** `review.requestLabel` is the real `on-request` mechanism, so every `labeled` delivery now reaches `normalize()`. An *issue* label still falls out with a null type, and the router hard-ignores every PR label that is not the configured one, so the widening costs a normalize call rather than a dispatch — but a deployment counting webhook deliveries by response body will see `{ filtered: true, reason: "unmapped event" }` where it used to see `{ filtered: true, reason: "action=labeled" }`.
- **Re-running the `last-light/review` check is now a review *request*, not a synchronize.** `check_run.rerequested` on that check name normalizes to `pr.review_requested` instead of `pr.synchronize`. Without this the button advertised on the `on-request` placeholder check would be a no-op: `pr.synchronize` is a PR-attention event, which `on-request` and `after-checks` both defer. A Re-run on anybody *else's* check still means "the checks changed" and still maps to `pr.synchronize`.
- **`getChecksConclusion` / `getChecksSummary` / `getBaseChecksState` take `{ excludeApp }`, and every trigger-side caller passes `botName`.** This is the self-gating deadlock fix and it is not optional: the aggregate covers *every* check run on the head SHA, ours included, so a `last-light/review` sitting `queued` (waiting for CI under `after-checks`) or `in_progress` pinned the aggregate at `pending` — the settle event never fired, the review never ran, the check never concluded, and a repo that made the check *required* had an unmergeable PR forever. The same loop reached `pr.checks_passed` on a Dependabot PR. Applied uniformly: the PR snapshot (head **and** base), the webhook connector's settle gate, the router's dependency-comment enrichment, and both dependency sweeps. Commit statuses carry no app and we never post one, so nothing is excluded there; excluding ours can never turn red into green.
- **The `last-light/review` check is now posted for *every* pr-review route, and completed from the run's terminal transition.** Two changes an operator sees. (1) A cron-, comment-, Slack- or CLI-triggered review used to post **no check at all**; it now posts one wherever `review.postsCheck` is on. (2) The check no longer strands `in_progress`. It was completed inside a `.then()` chained onto an in-memory promise, so it survived neither a deploy mid-review, nor a queued-then-resumed run, nor an `expireStaleRuns` cancellation, nor a crash — and the reason nobody noticed is that `check-prs-awaiting-review` re-reviewed within 30 minutes and posted a *superseding* check. That accidental repair is incompatible with the per-SHA review dedup this phase adds, because a check strands most often on a review that ran and posted, which is exactly the state the dedup skips. The lifecycle now hangs off a `TerminalRunObserver` on `WorkflowRunStore`, so `simple.ts`, `resume.ts`, `expireQueued` and the admin cancel all resolve it, and the id lives on `workflow_runs.scratch.reviewCheck`.
- **The check's conclusion is read from the review we actually posted, not from the run's exit code.** A `succeeded` run that legitimately skipped now concludes `neutral` rather than inheriting the old `!result.success ? "neutral"` shape; a `failed` run concludes `neutral` with "Review didn't complete"; a `cancelled` run concludes `cancelled`. All three pass branch protection except `failure` (a `CHANGES_REQUESTED` review), so a review that could not run never blocks a merge on its own.
- **With `postsCheck` on, a *deferred* review leaves a placeholder check.** `after-checks` posts a `queued` check ("Waiting for CI to finish before reviewing") so branch protection can require `last-light/review` without racing the settle event; `on-request` posts a `neutral` one whose Re-run button is the request affordance. Placeholders are posted **only on PR-attention events** — a placeholder is a statement about a head SHA, and the 30-minute sweep would otherwise re-post one per tick for the life of the PR. A plain skip (draft, already-reviewed, run-in-flight) posts nothing at all: 09 → S2 is explicit that a run which never dispatches must not create a check and immediately conclude it.
- **`check-prs-awaiting-review` now runs with webhooks enabled.** Its `condition.unless: webhooksEnabled` is gone. It is load-bearing in three ways the original plan did not account for: it is the release mechanism for every PR whose fix chain ended without pushing (attempts exhausted, `infra-dependent`, a `flaky` deferral, `upstream-broken`, or a crash — no new commit exists, so no further `check_suite` will ever fire); it is the re-pickup that makes the PR-scoped lock's drop-on-conflict safe; and it supersedes a `queued` placeholder whose settle event was never delivered. **Every webhook-enabled deployment gains a sweep it did not have**, every 30 minutes, bounded by `maxPerRepo` (25) and the global admission cap.
- **`jobs.ts`'s `condition.unless` is a predicate map, not a literal string compare.** An unrecognised name now **registers** the cron (the safe direction — a silently dropped cron produces no ticks, no rows and no error) and logs one warning per boot. Previously any value other than `webhooksEnabled` was silently ignored, which meant a typo turned a conditional cron into an unconditional one.
- **`review-discovery.ts` is a pure candidate finder.** Its draft filter and its per-candidate `getLatestBotReview` call are gone — both are fields of the one `PrState` snapshot `resolveReviewTrigger` decides over. Two consequences: `ReviewDiscoveryClient` lost `getLatestBotReview` (a fork of that module must drop it), and `maxPerRepo` now caps **candidates offered** rather than runs dispatched. On a repo whose open PRs are mostly already reviewed, the sweep therefore resolves a `PrState` for each candidate and skips at the gate, where it previously spent one review lookup per candidate and dispatched nothing. Same order of API calls, moved one layer down, in exchange for the cron holding no policy.
- **`resolveReviewTrigger` returns three values, not two.** `dispatch | defer | skip`, and `Decision` gained an optional `review` field carrying the undegraded verdict. `defer` and `skip` are the same answer to "may this run" and different answers to "what should the check say", which is what `reviewCheckPlacement` maps. Anything asserting `"skip"` for the `on-request` / `checks-pending` / `after-checks-on-attention` branches sees `"defer"` now.
- **`review.afterChecks` still does not exist** (09 locked decision 14) and was not added.
- **`prompts/pr-review.md` was not added either.** §7.6 offered two routes for getting CI evidence into the review; option (a) was confirmed correct. `buildPhasePrompt` synthesizes the `Context:` block from `Object.entries(fullCtx)` — it is not a fixed field list — and `renderContext` already seeds `checksState` and `ciSection` onto every PR-scoped run's context, `pr-review` included. So the evidence was already reaching the prompt and only the skill had to learn to use it. That is also why it benefits every skill-only phase for free.
- **`skills/pr-review/SKILL.md` gained a "Read what CI said" step and lost the `mode: scan` branch** (bumped to 7.1.0). The scan mode was removed when discovery moved into code; the instruction was dead weight the model still read on every run. An overlay that forked this skill keeps its own copy and will neither read the CI evidence nor drop the dead branch.
- **`GitHubClient.createCheckRun` gained `status` / `conclusion` options.** Default is unchanged (`in_progress`), and a `queued` check deliberately carries no `started_at`.

## Follow-up — the medium-severity review findings (issue #256)

Landed after the phases above, from a completeness review of the branch. Every entry here is a behaviour change on top of what the phase sections describe.

- **Both harness-owned scratch files moved into the checkout's `.git/`.** `<repo>/.git/lastlight-verify.sh` and `<repo>/.git/lastlight-notes`, stated once in `src/engine/fix-scratch.ts`. They previously sat at the checkout root and stayed out of the pull request because each sandbox backend registered them in that checkout's local `.git/info/exclude` — and the kubernetes backend never got that code, so on k8s the harness's own files were committed into the dependency PR by the agent's `git add -A`. `.git/` is the repository, not the work tree: no pathspec walk enters it, so `git add -A` cannot see either file on any backend with nothing to register anywhere. The failure mode of a backend forgetting is now a *stale gate*, which is recoverable and locally visible, rather than a *committed file*, which is neither. **Migration: an overlay that forked `skills/fixing/SKILL.md` or any of `prompts/{diagnose-ci,pr-fix,dependabot-ci-fix}.md` must be re-forked** — the packaged prompts now render the gate path from `{{verifyScript}}` and the journal path from `{{notesFile}}`, so a re-fork stays correct through any future move. `excludeFromGit` lost its `kind` parameter (every remaining caller registers a directory), and the kubernetes clone-init performs the same per-attempt delete the host backends do.
- **PR-scope is workflow metadata: `pr_scoped: true`.** The set of workflows crossing the PR-scoped dispatch gate — the run lock, the per-head-SHA dedup, escalation, the `PrState` snapshot — is derived from each workflow's own YAML key (`prScopedWorkflows()`, `src/workflows/pr-scope.ts`) rather than from a hardcoded list of four names. It had to move because the handlers are operator-configurable through `routes.github.*`: remapping `routes.github.pr_review` to a forked workflow silently dropped the entire gate for it, and every consequence of the gate is a *refusal*, so nothing looked wrong until two agents pushed the same branch. `validateAssets` now **warns at boot** when a configured `routes.github.pr_*` target does not declare the key. **Migration: none required** — the four original built-ins (`pr-fix`, `dependabot-ci-fix`, `dependabot-pr-merge`, `pr-review`) are still treated as PR-scoped without it, with a warning naming the file. An overlay that forked one of them, or that added its own PR workflow, should add `pr_scoped: true`.
- **Two `.lastlight/` policy leaves are now clamped.** `review.trigger` takes the **lower** tier on `on-request < after-checks < eager` (a repo committing `eager` against an `on-request` deployment was buying itself a full agent run per push, on the operator's budget), and `dependencies.auditComment` is **add-only `true`** (it is the audit record of a major this deployment auto-merged into that repo, so the party it silenced was the party being audited). Both were previously "free". A repo whose `.lastlight/lastlight.yml` sets either in the loosening direction now gets a `policy-downgrade` warning and the operator's value.
- **`fix.retryableClasses` is validated against the five diagnosis classes**, on the operator path and the repo path. An unknown member is dropped with a warning naming the five, and a list that ends up empty warns that no PR will be retried. It still degrades rather than throwing. A typo (`reproducable`) previously left a list that looked configured and made *every* diagnosis escalate `not-retryable` on the second dispatch. On the repo path a misspelt member is reported as `invalid-value`, not `policy-downgrade` — a typo and a policy decision are different problems. `DIAGNOSIS_CLASSES` moved to `packages/shared/src/config-types.ts` (both validators need it, and only `shared` is reachable from the CLI); `src/engine/fix-markers.ts` re-exports it, so no importer changes.
- **`fix.maxAttempts` / `localIterations` / `maxFlakyDeferrals` require whole numbers on the operator path**, matching the repo-layer clamp. `fix: { maxAttempts: 2.5 }` is now refused with a warning instead of leaving the two layers disagreeing about one leaf. `gateTimeoutSeconds` is a duration, not a count, and still takes any positive number.
- **A failed `getPullRequest` now skips instead of failing open.** Every other live read in `resolvePrState` still degrades to a value that cannot cause a skip; this one cannot, because its degraded values are all the permissive ones (`labels: []`, `isFork: false`, `headSha: ""`), so a 403 produced a snapshot that *looked* healthy and the cron route would dispatch a repo-write sandbox run against a pull request we knew nothing about. All three dispositions now take a `read-degraded` skip ahead of every other guard, including the run lock. It is transient like a lock drop — no label, no comment, no run row — and the cron re-pickup is what makes dropping sound.
- **The fork-PR notice is keyed on the decision and posted once per PR.** It previously keyed on `state.isFork`, which is true on *every* skip a fork PR takes, so a fork PR dropped by the run lock, by a deferred review or by the head-SHA dedup each earned "I can't apply fixes to this PR" — once per skip, for the life of the PR. It now keys on the typed `fork-pr` decision and de-duplicates through a persisted record (`PrState.forkNoticedAtSha`, written by a `fork-pr` run row) exactly as escalation does. Unlike an escalation it is never invalidated by a push: a fork stays a fork.
- **The cost budget bounds the current problem, not the PR's lifetime.** `fix.maxCostUsd` now measures spend since the last `sameProblem` boundary — the same boundary that re-arms `attempt`. Past the ceiling, a maintainer's push used to re-arm the attempt counter, clear the `escalated:` guard, and then fall straight back through `budget-exhausted` and post *another* `requires-human` comment — a comment whose own closing paragraph tells the maintainer that pushing is the remedy. `PrState` gained `costBaselineUsd`; a PR mid-flight at upgrade carries no baseline and so reads its full lifetime spend, which is the old behaviour for the one case where it was right.
- **A repo's `review.requestLabel` fires from the webhook.** The `pr.labeled` router branch read the operator's value only, and the shipped default is `null`, so every label event was dropped before any repo layer resolved — a key documented as repo-settable on both doc surfaces did nothing. The router now reaches the repo layer through the same injected `resolveRepoPolicy` seam the dispatch gate uses (one cached resolution per label event) and honours the operator's label **or** the repo's. Every other label is still a hard router-level ignore.
- **`fix.localIterations` and `fix.gateTimeoutSeconds` are wired.** Both were parsed, per-repo clamped, CLI-displayed and read by nothing: the operative numbers were literals in `pr-fix.yaml` / `dependabot-ci-fix.yaml`, whose comments asked a human to keep the two in step. The phase schema's `timeout_seconds` and `generic_loop.max_iterations` now also accept `{ from: <context path>, default: N }`, and both fix workflows use it. `from` resolves against the run's effective — already repo-clamped — `fix` block, so a repository that lowered its budget is honoured; `default` is the packaged value, used verbatim (with a warning) when the path resolves to nothing usable. An object rather than a bare `"{{fix.localIterations}}"` because an unresolved template renders to the empty string, which would leave the engine inventing a kill timeout for a phase it knows nothing about. **Migration: a deployment that set either key was previously getting the packaged behaviour regardless — it now gets what it asked for.** Check the value before upgrading if you set one experimentally.
- **The push gate is recorded on the run row.** The marker harvest reads `.git/lastlight-verify.sh` onto `scratch.fixMarkers.verifyScript` (bounded at 8 KiB, head kept) for the fix family, and the admin run detail panel renders it. A read, not a drain — unlike the journal, this file is the live gate the next loop iteration runs. This is 09 §S1's item 1: the gate is authored by the agent being gated and `until_bash` only reads its exit code, so recording it is what makes that bounded hazard *inspectable* rather than a guess after the workspace is reset. Deliberately still not validated — checking the contents is an arms race against your own agent. Inert on the kubernetes backend, like the journal.
- **The admin run detail panel shows the `PrState` snapshot (09 §S3).** For any run carrying `context.prState`, the panel renders the facts the dispatch decision was taken on, the `{decision, reason}` pairs recorded on the row, the journal and the gate above. It recomputes nothing: a reason appears only where a decision produced one, and the raw snapshot is one click away, so a field added to `PrState` is visible without a dashboard change. The per-repo Config tab also renders `fix` / `dependencies` / `review`, which the endpoint had been returning with provenance while the dashboard's hand-mirrored types silently omitted them; `tests/admin/dashboard-config-mirror.test.ts` now fails on that drift.
- **The fix prompts render four context variables that reached no prompt before.** `flakyPromoted` / `flakyDeferrals` / `maxFlakyDeferrals` now produce an explicit block on the promoted run — previously the agent got no signal that its `flaky` verdict would be ignored, so it diagnosed `flaky` again and the fix phase ran against a diagnosis saying "change nothing". And `prompts/diagnose-ci.md` branches on a new `ciLogsUnavailable` (true only when there *is* a CI report and its logs are missing, so a green PR is not warned about a download never attempted), which is the fact `skills/fixing/SKILL.md` already told the agent to report. An overlay that forked those prompts picks none of this up.
